# 签约进度模块采用管理员手动录入合同而非自动生成

_来源：e1e55ae → c750ce2 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
Step 3 签约进度模块原计划包含合同编码自动生成逻辑。根据最新业务反馈，合同来源主要为品牌商管理员手动新建/编辑，核心需求是追踪签署进度而非生成合同本身，且需复用 Step 2 的文件管理体系。

## 决策驱动
- 业务灵活性
- 开发复杂度控制
- 需求范围收敛

## 备选方案
- **管理员手动录入合同** — 优点：适应线下已存在合同的场景，灵活性高；无需实现复杂的分布式锁和序列生成逻辑；可复用现有的文件上传组件。；缺点：依赖人工操作，需增加数据校验防止重复或错误。
- **系统自动生成合同编码与记录** _（已否决）_ — 优点：规范化程度高，减少人工错误。；缺点：实现复杂（需处理并发、分布式锁）；无法兼容线下已签署或特殊编码规则的合同；偏离当前“追踪进度”的核心目标。

## 决策
移除合同编码自动生成的后端逻辑（如 SELECT FOR UPDATE）。新增管理员手动创建/编辑合同的 API (`POST /opshub/signing/create`, `PUT /opshub/signing/update`) 及前端弹窗组件 `ContractFormModal.vue`。合同附件上传复用 `ops_basedata_file` 表（category='contract'）。移除导入/导出功能，聚焦于核心的签署状态追踪。

## 影响
简化了 Step 3 的后端实现，避免了分布式锁等复杂并发控制。系统将更依赖于管理员的操作规范性，需在 UI 层加强合同编码唯一性等校验提示。
