# 建立跨模块的通用附件表 ops_cs_attachment

_来源：3722ab2 → 11502cc 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
系统中多个模块（工单、操作请求、基础数据、签约、订单、售后）均需要附件存储功能。若每个模块独立设计附件表或存储逻辑，会导致数据模型冗余、维护困难以及前端上传组件的重复开发。

## 决策驱动
- 数据模型统一：避免多张结构相似的附件表
- 开发复用：前端和后端可共用一套附件上传/查询/删除接口
- 扩展性：新模块接入附件功能只需关联 module 和 business_id

## 备选方案
- **通用附件表 ops_cs_attachment** — 优点：一张表存储所有模块附件，通过 module 和 business_id 关联；统一的 CRUD 接口；便于全局管理附件生命周期。；缺点：单表数据量可能随时间快速增长，需考虑索引优化和未来分表策略；不同模块对附件的业务含义不同，通用表难以承载模块特有的附件元数据（但可通过 remark 字段扩展）。
- **各模块独立附件表** _（已否决）_ — 优点：数据结构可高度定制化，隔离性好。；缺点：代码重复率高，维护成本高；新增模块需重复开发附件功能。

## 决策
新建通用附件表 ops_cs_attachment，包含 module（关联模块标识）、business_id（业务ID）、file_url 等字段，并为工单、操作请求及后续所有模块提供统一的附件管理服务。

## 影响
实现了附件功能的标准化和复用。需注意在查询附件时严格校验 module 和 business_id 的权限，防止越权访问其他模块的附件。随着数据量增长，需监控 idx_ops_cs_attachment_module_biz 索引的性能。
